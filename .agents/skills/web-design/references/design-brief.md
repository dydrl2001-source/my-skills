# A useful design brief

Use the following dimensions to find gaps, not as seven mandatory interview rounds. Reuse what the user and project already establish. A prompt-only request ends with the brief; an implementation request carries these decisions into the existing project.

| Dimension | Concrete output |
| --- | --- |
| Purpose and audience | Who arrives, what they need, and the action that means success. |
| Journey | The few steps from entry to that action, with the information and friction at each step. |
| Evidence and content | Available facts, images, copy and required sections. Separate supplied facts, verified research, design assumptions and placeholders. |
| Brand and visual direction | Existing brand constraints or a small coherent set of colors, fonts, spacing and imagery. State why it fits the audience. |
| Components | The necessary sections, reusable components and responsive behavior. Preserve explicitly requested section counts. |
| States and action | CTA destination/service and relevant focus, loading, success, empty and error states. |
| Completion | What the user should be able to do, and which viewports or interactions need checking. |

For a prompt handed to another builder, include the requested output type, project constraints and known content. Keep unknown business facts explicitly unknown. Research requires actual source access; do not convert imagined competitors, prices or customer testimonials into evidence.

For a landing page, introduce the value and show the next action early. Add benefits, detail, proof, FAQ or reassurance only where available information and audience questions justify them. A fixed marketing framework does not require invented proof, eleven sections or a new framework dependency.

For a small modification, a short note such as “reuse the current application service, add its existing button pattern, and confirm pending/success/error behavior” is enough. Do not turn every button request into a site redesign.
