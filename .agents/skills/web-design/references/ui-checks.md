# Check the changed experience

Choose checks that could expose a real failure in the requested change. Reuse existing project tooling. Do not add a test framework for a static copy change or claim an unrun browser check passed.

| Area | What to verify |
| --- | --- |
| Main action | The supplied route or existing service is connected; required input reaches it; errors and pending state follow the project pattern. Avoid real external submissions unless the task authorizes them. |
| Responsive view | Content and controls fit a narrow viewport and a representative wider one. Text remains readable without horizontal overflow. |
| Keyboard and semantics | Links navigate, buttons perform actions, focus is visible, form labels exist, and relevant interactions work without a pointer. |
| Content integrity | No invented testimonials, customer counts, unavailable images or unsupported outcome claims. Prototype placeholders remain visibly identifiable. |
| Visual consistency | Existing font, tokens, brand and section constraints are respected. Contrast and spacing support the hierarchy. |
| Motion and media | Useful alternative text, stable image layout, no essential information encoded only in motion, and reduced-motion support when motion exists. |
| Regression | Relevant existing build, type or behavior checks pass. State the checked scope and remaining limitations. |

When only a design brief was requested, check that the brief specifies the user's goal, constraints, content assumptions, primary action and appropriate states. Do not scaffold or deploy a product to demonstrate that a prompt was written.
